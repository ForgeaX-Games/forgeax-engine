Why recovery was needed

The main release job reported npm publish success while the public registry briefly still returned 0.1.4; both carrier version and tarball returned 404. Recovery rebuilt the carrier from the Release ZIP that had already passed ZIP verification, without rebuilding Engine, then polled the public registry. This distinguishes a completed publication request from a package users can actually download.

Version checks and upgrade risks

Each forgeax project new reports the current SDK version against the public registry:

{
  "status": "current",
  "currentVersion": "0.1.6",
  "latestVersion": "0.1.6"
}
  1. Read release changes and migration notes when a newer version is available.
  2. Existing games retain their versions; dependencies are not rewritten automatically.
  3. Create a verification project with the new SDK in a separate branch or copied directory.
  4. Migrate after doctor, tests, build, dev/preview, and required browser/RHI evidence pass.

Upgrades can change APIs, asset schemas, plugin Entries, and build tools; existing games require adaptation.

Pre-release checklist

  • Build/verification Engine commits match the target commit.
  • Publish ZIP, SHA256SUMS, SPDX, provenance, and verification results together.
  • The npm carrier includes a root README and excludes the store.
  • All internal @forgeax/engine-* dependencies use the same version.
  • Registry version, tarball, README, and integrity are actually visible.
  • The required-ci ruleset is active and exactly matches the repository manifest.
